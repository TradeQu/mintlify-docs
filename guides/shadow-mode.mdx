**Audience:** engineers and risk owners introducing or changing a policy in a live system who need to review its results before enforcing it.

Shadow mode runs a policy against real traffic and reports its violations. Today, those violations also feed the decision's severity ramp. A shadow policy can therefore escalate the live verdict, including to `DENY` when an enforcing policy also has a violation. Only a `DENY` whose violations are all from shadow policies is returned as `ALERT`.

<Warning>
  Until the fix ships, treat shadow violations as live: they can change the verdict your application receives.
</Warning>

We are changing this so shadow results never affect a live outcome. This page will be updated when the change ships.

<Info>
  **Console terminology** — In the MeshQu console UI this setting is labelled **"Advisory mode."** It is the same feature as the `shadow_mode` field described here; the API and SDK use `shadow_mode`. There is no `advisory_mode` field.
</Info>

> **Mental model:** MeshQu returns a verdict; your application decides what to do with it. Shadow violations currently contribute to that verdict. MeshQu does not block operations itself. See [Integration Patterns](/guides/integration-patterns).

## Why use it

- **Observe real violations** — review a new or tightened policy's results before promoting it. Its violations can still change the returned verdict.
- **Real traffic** — you observe how the policy behaves against production data, not synthetic cases.
- **Review before promotion** — use alerts to find false positives and tune thresholds before enforcing.

## The `shadow_mode` flag

`shadow_mode` is a boolean on the policy. When `true`, the engine still evaluates its rules and includes their violations in the decision. If every violation is from a shadow policy and the severity ramp returns `DENY`, the returned decision is `ALERT`. If any violation is from an enforcing policy, that conversion does not happen.

### Create a policy in shadow mode

<CodeGroup>

```bash cURL
curl -X POST https://api.meshqu.com/v1/policies \
  -H "Authorization: Bearer mqu_YOUR_API_KEY" \
  -H "X-MeshQu-Tenant-Id: YOUR_TENANT_ID" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "PAYMENT-LIMIT-V2",
    "name": "Payment Limit v2",
    "decision_type": "payment_approval",
    "shadow_mode": true,
    "rules": [
      {
        "code": "MAX-AMOUNT",
        "name": "Maximum Payment Amount",
        "rule_type": "threshold",
        "condition": { "field": "amount", "max": 100000 },
        "severity": "high"
      }
    ]
  }'
```

```typescript TypeScript
const policy = await meshqu.createPolicy({
  code: 'PAYMENT-LIMIT-V2',
  name: 'Payment Limit v2',
  decision_type: 'payment_approval',
  shadow_mode: true,
  rules: [
    {
      code: 'MAX-AMOUNT',
      name: 'Maximum Payment Amount',
      rule_type: 'threshold',
      condition: { field: 'amount', max: 100000 },
      severity: 'high',
    },
  ],
});
```

</CodeGroup>

### Promote to enforcing

When you are ready to enforce the policy, turn off shadow mode. Check the combined decision against your application logic before doing so.

<CodeGroup>

```bash cURL
curl -X PATCH https://api.meshqu.com/v1/policies/POLICY_ID \
  -H "Authorization: Bearer mqu_YOUR_API_KEY" \
  -H "X-MeshQu-Tenant-Id: YOUR_TENANT_ID" \
  -H "Content-Type: application/json" \
  -d '{ "shadow_mode": false }'
```

```typescript TypeScript
await meshqu.updatePolicy(policyId, { shadow_mode: false });
```

</CodeGroup>

## Reading shadow state from a verdict

Both `evaluate` and `record` return a `result` with a `decision` and `violations`. The `evaluate` response also has a top-level `shadow_mode` object whose `enabled` is true when the result reports that a shadow rule was evaluated, and whose `original_decision` is `DENY` when an all-shadow `DENY` was converted to `ALERT`. On a recorded decision, `result.is_shadow` indicates that a shadow rule was evaluated. Each shadow violation has `is_shadow: true`. If an all-shadow `DENY` was converted to `ALERT`, `result.shadow_converted` is `true` and `result.original_decision` is `DENY`. A shadow violation can also contribute to `REVIEW` or to a mixed-policy `DENY` without a conversion. See [Receipt Reference §1.1 and §1.6](/concepts/receipt-reference).

<Warning>
  An all-shadow `DENY` is returned as `ALERT`, but mixed shadow and enforcing violations can return `DENY`. Your application decides how to act on every returned verdict. See [Integration Patterns](/guides/integration-patterns).
</Warning>

## Monitoring the shadow period

Review which shadow rules fire and how they affect returned decisions. On recorded decisions, each shadow violation creates an alert at the rule's severity. These alerts do not carry a shadow marker.

```bash
# Alerts raised by the shadowed policy
curl "https://api.meshqu.com/v1/alerts?limit=50" \
  -H "Authorization: Bearer mqu_YOUR_API_KEY" \
  -H "X-MeshQu-Tenant-Id: YOUR_TENANT_ID"
```

Review each alert against the policy and the returned decision. Ask:

| Observation | Likely action |
| --- | --- |
| Alerts on operations that *should* pass | Threshold too tight, or rule too broad — tune it. |
| Alerts that correctly catch bad operations | Good signal — builds confidence to promote. |
| No alerts at all over real traffic | Rule may never fire — check field mapping and `decision_type`. |

Matching [webhook](/guides/webhooks) subscriptions receive these alerts too. Filter by `decision_type` and `severity_min` for your monitoring. Overview decision counts and compliance metrics also include recorded shadow decisions; they are not an enforcing-only view.

### Suggested shadow duration

Capture enough variety — different times of day, days of week, and edge cases — before promoting:

| Risk of the decision | Suggested minimum shadow period |
| --- | --- |
| Low (advisory alerts) | ~1 week |
| Medium (queued for review) | ~2 weeks |
| High (approvals, payments) | ~3–4 weeks |

These are guidelines, not enforced limits.

## Comparing against your existing logic

If you are replacing or supplementing a system that already makes the decision, you can run MeshQu *alongside* it before MeshQu becomes authoritative. This is a client-side pattern — it doesn't require any MeshQu feature beyond the `evaluate` endpoint:

```typescript
async function processPayment(payment: Payment) {
  // Your existing decision logic remains authoritative.
  const existingDecision = await yourExistingLogic(payment);

  // Evaluate with MeshQu in parallel and log the comparison (fire-and-forget).
  meshqu
    .evaluate({
      decision_type: 'payment_approval',
      fields: { amount: payment.amount, currency: payment.currency },
      metadata: { correlation_id: payment.id, existing_decision: existingDecision },
    })
    .then((res) =>
      logger.info({
        paymentId: payment.id,
        existingDecision,
        meshquDecision: res.result.decision,
        matches: existingDecision === res.result.decision,
      }),
    )
    .catch((err) => logger.warn({ err }, 'MeshQu comparison failed'));

  return existingDecision; // MeshQu does not affect the outcome yet
}
```

Don't block your critical path on the comparison call — fire it and forget it, or push the context onto a queue. Tag the evaluation with a `correlation_id` and your existing verdict in `metadata` so you can line the two up later.

<Note>
  Use `evaluate` (not `record`) for throwaway comparisons — it records no decision, so the comparison leaves no decision behind. Resolving the active policies may still persist a reusable policy snapshot and return its `policy_snapshot_id`; a repeat call resolving to the same policies creates no new snapshot. Switch to `record` once you want a durable, replayable audit trail of each decision. See [Evaluate vs Record](/concepts/overview#evaluate-vs-record).
</Note>
