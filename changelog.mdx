<Info>
MeshQu is currently available for research, evaluation and design-partner deployments. Production availability and support commitments are agreed per engagement. This changelog documents API and SDK functionality shipped into those deployments. Console UI changes are not tracked here.
</Info>

MeshQu follows [Semantic Versioning](https://semver.org/). The **API contract version is `v1`** — the `/v1` URL prefix, which is stable and only changes on a major release. The current **release** (this changelog's latest entry, the OpenAPI spec `info.version`, and the API package version) is **1.28.0**.

## Versioning policy

- **Major** (`v2.x`): Breaking changes to request/response contracts or authentication. Announced with a migration guide and deprecation period.
- **Minor** (`v1.2`): New endpoints, fields, or features. Backwards-compatible.
- **Patch** (`v1.1.1`): Bug fixes and performance improvements. No contract changes.

## Stability guarantees

- Existing response fields are never removed or renamed within a major version.
- New optional fields may be added to responses at any time — clients should ignore unknown fields.
- Webhook payload schemas follow the same policy.

## API version header

All endpoints are prefixed with `/v1`. When a new major version is released, the previous version will remain available for a documented deprecation period.

## v1.28.0

**Ratify checks what was reviewed and its body is closed, and the audit
actions gain a value.** Three requests to
`POST /v1/policies/{id}/versions/{version}/ratify` that used to succeed are now
refused. No operation is added or removed and no response status changes. What
a request may contain changes in two places: the ratify body is now closed, and
the `action` filter on `GET /v1/audit-log` accepts one more value. The reference
descriptions of draft discard and key creation are rewritten to state behaviour
that 1.26.0 introduced.

**1.27.0 was not released.** Its change, a new audit `action` value, ships in
this release. This release follows 1.26.0 directly.

**Callers that relied on the old behaviour.** A ratify request that used to
succeed is now refused when its body carries a key other than
`expected_revision`, `approval_authority` and `ratifier_role` (400), when the
active rules of the version changed since its latest sealed submission was
sealed and the newest review record on that submission is an ACCEPT (409), or,
when no seal of the version or of a draft it supersedes was made under an
authoring capability, when the newest review record on its latest sealed
submission is `CORRECT_AND_RESUBMIT` or `STOP` (409). Separately, a client that
treats the list of audit actions as closed, for example by validating `action`
against the values the reference listed before, will reject an event that
carries the new value.

**Ratify**

- **The body is closed.** A body with any key other than `expected_revision`,
  `approval_authority` and `ratifier_role` is refused
  **400 `FST_ERR_VALIDATION`**, and nothing is ratified. Before, an unknown key
  was accepted and ignored. `expected_revision` is still required. A request
  authenticated by an API key is still refused 403 `HUMAN_PRINCIPAL_REQUIRED`
  before the body is checked, and a key without `policies:write` still gets
  403 `FORBIDDEN` first.
- **A version whose reviewed rules changed is refused.** When the newest review
  record on the version's latest sealed submission is an ACCEPT, the version's
  current active rules must still hash to the `active_rules_hash` that
  submission sealed. A change to the active rules since the submission was
  sealed is refused, including reordering them: the hash is taken over the
  active rules in stored order. The answer is
  **409 `REVIEWED_SUBJECT_STALE`**, with `details.submission_id`,
  `details.review_record_id`, `details.sealed_active_rules_hash`,
  `details.current_active_rules_hash`, `details.candidate_revision` and
  `details.draft_revision`. Nothing is ratified. Seal the current rules and
  have them reviewed again, or restore the rules that were accepted. Before, a
  change to the active rules after the seal did not stop the ratify. This
  applies whether or not an authoring capability sealed the version.
- **A version whose latest review is adverse is refused.** When no seal of the
  version or of a draft it supersedes was made under an authoring capability,
  and the newest review record on its latest sealed submission is
  `CORRECT_AND_RESUBMIT` or `STOP`, the answer is
  **409 `RATIFY_REVIEW_ADVERSE`**, with `details.reason` set to that
  disposition and `details.submission_id` and `details.review_record_id`.
  Nothing is ratified. Before, it was ratified. When a seal was made under an
  authoring capability, the same records are still refused
  409 `RATIFY_NO_ACCEPT_RECORD`, as before.
- **What these checks do not cover.**
  - Only the hashed fields of the active rules (`code`, `condition`,
    `severity`, `when`) are compared. A change to a rule's name, description,
    `source_ref`, `replaces_rule_code` or `rule_type`, or to the content of a
    rule that is inactive before and after, is not refused. Making a rule
    active or inactive does change what is compared.
  - Neither refusal applies to a version with no sealed submission, or whose
    latest sealed submission has no review record. Where an authoring
    capability sealed the version or a draft it supersedes, such a version is
    still refused 409 `RATIFY_NO_ACCEPT_RECORD`, as before.
  - A version that can no longer be ratified, such as one already ratified, is
    still refused 409 `INVALID_TRANSITION`.
  - A request whose `expected_revision` is stale is still refused
    409 `STALE_DRAFT_REVISION` first.
- **The `policy_ratified` audit entry cites the ACCEPT.** When a ratification
  relied on an ACCEPT, the entry's `changes` carries `review_record_id` and
  `review_submission_id`, whether or not an authoring capability was involved.
  Before, only a ratification under the review gate carried them.

**Audit actions**

- **`connection_consented` is a new audit `action` value.** No operation in
  this reference records it, so the reference does not say when it appears.
- **Where it can appear.** As `action` on the events returned by
  `GET /v1/audit-log`, `GET /v1/admin/audit-log` and
  `GET /v1/audit-log/entity/{type}/{id}`.
- **As a filter.** `GET /v1/audit-log` accepts it as the `action` query
  parameter. Before, it was refused like any other value that is not a listed
  audit action: 400 `FST_ERR_VALIDATION`.

**Reference descriptions**

These change what the reference says, not what the API does.

- **`DELETE /v1/policies/{id}/versions/{version}`.** The description now states
  the 1.26.0 behaviour: only a verified human session may discard, an API key is
  refused 403 `HUMAN_PRINCIPAL_REQUIRED` (after the `policies:write` scope
  check), and a tenant admin may discard a draft that is not theirs in three
  cases, each with a `reason`. Before, it said an API key never takes the admin
  path and that a draft whose author key is still live is refused.
- **`POST /v1/api-keys` and `POST /v1/admin/api-keys`.** The `scopes` and `role`
  descriptions now state the refusals 1.26.0 introduced
  (`API_KEY_SCOPE_ESCALATION` and `API_KEY_ROLE_ESCALATION`), the default
  scopes and the default role, and that a human session caller is not bounded.
  The default role depends on a deployment setting. Before, `scopes` said only
  that it defaulted to "read + evaluate", and `role` had no description.
- **Still described only in the v1.26.0 entry.** The reference does not yet
  describe the refusal of a ratify for an archived policy's version,
  `permissions.canDiscard` on `GET /v1/policies/{id}`, `INVALID_PARENT` on
  `POST /v1/admin/tenants`, or the duplicate `unit_id` refusal on the
  `codification` block.

## v1.26.0

**Clearer refusals across key, licence, capability, discard, ratify, tenant and
codification writes.** Most changes below replace a status a caller already
got on the same input, whether a success, a bare 500 or a misleading 404, with
a named refusal. One widens who may discard a draft. The set of routes and
their request schemas are unchanged.

**1.25.0 was not released.** This release follows 1.24.0 directly.

**Callers that relied on the old behaviour.** Six requests that used to
succeed are now refused: revoking a key that is already revoked (409),
creating a key that asks for more than the calling API key holds (403),
discarding a draft with an API key (403), ratifying a version of an archived
policy (409), issuing a licence with a future start while the key's governing
licence is in force (409), and a `codification` block that repeats a `unit_id`
(422).

**This entry is the current statement of some of these behaviours.** The
OpenAPI reference is regenerated for this release. It carries the revoke-key
409 and the licence and capability changes below, apart from UUID letter case.
The reference descriptions of the other routes named here (key creation,
draft discard, `GET /v1/policies/{id}`, ratify, tenant provisioning and the
`codification` block) are unchanged in this release, so they do not yet
describe the changes below. Key creation and draft discard are described in the
reference from v1.28.0.

**API keys**

- **Revoking a key that is already revoked is refused.**
  `DELETE /v1/api-keys/{id}` and `DELETE /v1/admin/api-keys/{id}` answer
  **409 `API_KEY_ALREADY_REVOKED`**, with `details.revoked_at` giving the
  revocation that stands. Nothing is written: the original revocation time and
  actor are kept and no second audit entry is appended. Before, the second
  call answered 200 or 204 and overwrote the revocation time and actor. An
  unknown key is still 404 `NOT_FOUND`. The reference now declares the 409 on
  both routes.
- **Creating a key: an API key cannot ask for more than it holds.**
  `POST /v1/api-keys` and `POST /v1/admin/api-keys`, when the caller is an API
  key:
  - Every requested scope must be one the calling key holds, otherwise
    **403 `API_KEY_SCOPE_ESCALATION`**, with the scopes it lacks in
    `details.exceeding_scopes`.
  - The requested `role` must be one the calling key's role may create,
    otherwise **403 `API_KEY_ROLE_ESCALATION`**, with `details.requested_role`
    and `details.minter_role`. `admin` may create any role; every role may
    create itself and `viewer`; `operator` and `auditor` may not create each
    other.
  - An omitted `scopes` or `role` is checked as the value it would default to.
    A request whose default exceeds the calling key is refused, not narrowed.
  - **What this does not cover.** A request from a verified human session is
    not bounded this way. The expiry of the new key is not bounded by the
    calling key's. And the check applies to these two routes only: it does not
    change what any other route lets the holder of a key grant.

**Licences and capabilities**

These changes are on `POST /v1/agent-licences`,
`POST /v1/agent-licences/{id}/revoke`, `POST /v1/authoring-capabilities` and
`POST /v1/authoring-capabilities/{id}/revoke`.

- **`POST /v1/agent-licences`: a version that is not in force.** When the
  named version exists, matches `policy_id` and `policy_version_number`, and is
  not ratified and in force, or its policy is archived, the answer is
  **409 `AGENT_LICENCE_POLICY_VERSION_NOT_IN_FORCE`**. It used to be a 500.
  Nothing is issued. A `policy_version_id` that does not exist, or does not
  match the policy and number named, still answers 500.
- **`POST /v1/agent-licences`: a future start while a licence is live.** A
  `valid_from` after now, for a key whose governing licence is in force now, is
  refused **409 `AGENT_LICENCE_FUTURE_START_WHILE_LIVE`**, with
  `details.live_licence_id`, `details.live_valid_until` and
  `details.requested_valid_from`. It used to be a 201 that would govern at
  once and leave the key with no valid licence until its start. Nothing is
  issued. The governing licence is the most recently issued one for the key. A licence
  that starts now is not refused for this reason, and neither is a future start
  for a key whose governing licence is not in force.
- **The four routes: a committed write whose read-back failed.** When the
  read after the commit returns nothing, or itself fails, the answer is
  **500 `AUTHORING_CAPABILITY_READBACK_FAILED`** or
  **500 `AGENT_LICENCE_READBACK_FAILED`**, with `details.committed` set to
  `true`. The record exists: `details.licence_id` or `details.capability_id` is
  its id. On the revoke routes that id is the revocation record, and
  `details.revokes_licence_id` or `details.revokes_capability_id` names the
  grant being revoked. Do not repeat the request: a second licence issue would
  govern in place of the first, and a repeated revoke is refused 409. Before,
  these answered a 404 `*_NOT_FOUND` or a bare 500. A 404 on these routes means
  nothing was written.
- **The four routes: UUID letter case.** The UUIDs these routes take, that
  is `key_id`, `policy_id` and the version id (`policy_version_id` or
  `source_policy_version_id`) in the body, and the grant id in the revoke path,
  are lower-cased before use, so an upper-case spelling names the same record
  as the lower-case one. Before, an upper-case `policy_id` on
  `POST /v1/authoring-capabilities` was refused as not found for a version that
  exists, and a licence issued with upper-case ids was accepted but then failed
  integrity verification when read.

**Policies**

- **Discarding a draft is a human act.**
  `DELETE /v1/policies/{id}/versions/{version}` now refuses a request
  authenticated by an API key with **403 `HUMAN_PRINCIPAL_REQUIRED`**,
  before the route looks at the draft. That includes a key that authored the
  draft, which could discard it before. The scope check runs first: a key
  without `policies:write` still gets 403 `FORBIDDEN`. A verified human session
  reaches the route as before. `HUMAN_PRINCIPAL_REQUIRED` is the refusal
  ratify, reject and activation already give an API key.
- **A tenant admin may discard an unbound draft that an API key created.**
  With discard closed to keys, a tenant admin's human session may discard a
  draft that is bound to no authoring capability and whose creation record in
  the audit chain names one of the tenant's API keys as the actor, whether or
  not that key can still act. Before, this needed a key that could no longer
  act (revoked, inactive, or failing capability verification), and a draft
  whose author key was still live was refused. The body must carry
  `{ "reason": string }` (400 `DISCARD_REASON_REQUIRED` without it), and the
  reason is recorded in the audit chain. Nothing is exhausted, because nothing
  is bound. A draft whose creation record names a person, names no key of the
  tenant, or cannot be resolved to a single record is still refused this way.
- **`GET /v1/policies/{id}` no longer offers a key a discard it would be
  refused.** For a request authenticated by an API key, `permissions.canDiscard`
  is `false` and `actions` does not include `discard`.
- **Ratify refuses a version whose policy is archived.**
  `POST /v1/policies/{id}/versions/{version}/ratify` answers
  **409 `INVALID_TRANSITION`** with `details.reason` `POLICY_ARCHIVED`, the
  code and reason activation already gives for an archived policy. The
  version stays as it was and nothing is recorded. Before, the ratify
  succeeded, leaving a ratified version that activation then refuses.
- **A `codification` block that declares one `unit_id` on two clauses is
  refused.** On `POST /v1/policies`, `POST /v1/policies/{id}/versions`,
  `POST /v1/policies/{id}/versions/{version}/supersede` and
  `POST /v1/policies/{id}/versions/{version}/supersede-assigned`, a
  `codification.clauses` list with the same `unit_id` on more than one clause
  answers **422 `CODIFICATION_REFUSED`** with `details.code`
  `DUPLICATE_UNIT_ID`. Nothing is stored. Before, the later clause silently
  replaced the earlier in the lookup, so one outcome accounted for both. `unit_id`
  values are compared exactly, so `u-1` and `U-1` are two clauses. A version
  already stored with a duplicate is not rewritten.

**Tenants**

- **`POST /v1/admin/tenants`: a `parent_tenant_id` that names no tenant.** A
  well-formed `parent_tenant_id` that matches no tenant answers
  **422 `INVALID_PARENT`**. It used to be a 500. The existing cycle and depth
  refusal is unchanged.

## v1.24.0

**A seal precondition against a late or duplicated request.** The review-submission
seal route now accepts an optional-but-often-required field that lets a caller
tell the server what it already knew, so a stale or repeated seal attempt is
refused instead of creating a second sealed submission.

- **`expected_latest_submission_id` on `POST /v1/policies/{id}/versions/{version}/review-submissions`.**
  Send the `id` of the latest sealed submission of this policy version that
  you read before deciding to seal (the first item returned by
  `GET /v1/policies/{id}/versions/{version}/review-submissions`), or `null`
  when that list was empty. The server compares it, inside the seal's own
  locks, with its own record of the version's latest submission.
- **A mismatch is refused, and nothing is written.** A disagreement is
  **409 `STALE_LATEST_SUBMISSION`**, with `expected_latest_submission_id` in
  `details`. No submission is created. `details.latest_is_this_package` is
  also included: it tells you whether the latest sealed submission — the one
  that won — holds the same package this request would have sealed, so you
  can tell an intended-but-overtaken seal from a genuinely different one. A
  legitimate further seal (after a return, or a deliberate second package)
  simply names whichever submission is latest at that point and seals as
  usual.
- **A safe re-send.** Because the field is compared under the same locks the
  seal itself takes, two requests carrying the same value can never both
  succeed — the first to commit moves the latest, and the second is refused.
  So re-sending the exact same request after a timeout or a dropped response,
  without re-reading anything first, cannot seal the same package twice.
- **Required for capability-admitted requests.** When the request was admitted
  by an authoring capability, the field is required: omitting it is refused
  **400 `EXPECTED_LATEST_SUBMISSION_REQUIRED`**. For every other caller it is
  optional — checked when sent, and the route behaves exactly as before when
  it is not.
- **What this does not cover.** This precondition is about the *latest
  submission*, not the draft's rule content — that is what the existing
  optional `expected_draft_revision` field, and its own `409 STALE_DRAFT_REVISION`
  refusal, continues to guard. Sending both narrows what a seal can silently
  overtake; sending neither leaves the route's pre-1.24.0 behavior unchanged.

## v1.23.0

**A server-side bound on authoring writes.** Four write routes now run under a
server-side time bound, and a write that cannot finish inside it is rolled
back and reported, rather than left to run indefinitely behind a lock.

- **Affected routes:** `PATCH /v1/policies/{id}/versions/{version}`,
  `POST /v1/policies/{id}/versions/{version}/review-submissions`,
  `POST /v1/policies/{id}/versions/{version}/supersede-assigned`, and
  `POST /v1/review-submissions/{submissionId}/withdrawal-requests`.
- **The bound.** Each of these routes now waits at most 2 seconds for any
  database lock it needs, and the server abandons the write if it is not
  ready to commit within 4 seconds of the server beginning to handle the
  request. A write that hits either limit is rolled back — nothing is
  written — and the request fails with **503 `AUTHORING_WRITE_CONTENDED`**,
  including `details.committed: false`, a reason, and a `Retry-After` header.
  This response is a definite non-commit and is safe to retry.
- **What this does not mean.** A 503 `AUTHORING_WRITE_CONTENDED` is the only
  response that tells a caller its write did not commit. A client-side
  timeout on any of these routes does not: the bound above is measured from
  when the server began handling the request, which a client cannot observe,
  and nothing bounds how long a request takes to reach the server. If a
  request to one of these routes times out on the client, the client cannot
  conclude — from the timeout alone — that the write did or did not commit.
- **Scope.** Only these four write routes carry the bound. Other write routes
  are unaffected by this change.

## v1.22.0

**Active-rules hash on the policy version read.** An additive field: every
response that carries a policy version now includes a hash of that version's
current active rules.

- **`active_rules_hash`** is added to `GET /v1/policies/{id}/versions/{version}`,
  the versions list, and every other response that embeds a policy version
  (create, patch, reopen, set-aside, supersede, submit, reject, recall and
  ratify). It is computed the same way the review-submission seal computes its
  own `active_rules_hash`, so the two values can be compared directly.
- **What it covers.** The hash is derived from each active rule's code,
  condition, severity and when-clause, in stored order. Editing a rule's name,
  description or other non-evaluated metadata does not change it, and adding a
  new inactive rule does not change it either — only a change to an active
  rule's code, condition, severity or when-clause, or a change to which rules
  are active, moves the hash.
- **Always present on 1.22.0 responses.** Every policy version has this field
  from this release on. Servers older than 1.22.0 omit it — clients should
  treat a missing field as unknown, not as a specific value.

## v1.21.0

**The capability-scoped pending-work read.** A read release: an
authoring-capability key can now read its own pending work directly, without a
human session or a broader key.

- **New: `GET /v1/authoring-capabilities/current/pending-work`.** For an API
  key holding only the `authoring:capability` scope, whose capability grants
  both `policy.read` and `review.retrieve`, this returns:
  - `items`: the `GET /v1/work/pending` items (the same item schema) for the
    governing grant's policy version, plus — only when a grant of the same
    capability chain, on the same policy, names it — the items of at most one
    earlier draft: the lineage-previous version the head's next seal is bound
    to.
  - `next_seal_answers` (optional): the one return the next seal of this
    version must name as `answers_record_id`. Present only while the version
    is draft or submitted.
  - `returns_not_answerable`: unanswered returns in view that no seal can
    currently answer, each with a `reason` of `not_lineage_previous` or
    `head_not_sealable`. Informational, not a task list.
  - `capability_id`, `root_capability_id`, `policy_id`, `policy_version_id`,
    `policy_version_number`, and `observed_at` (server time at the start of
    the read — the response is not a snapshot).
  - Optional flags `lineage_unresolved` (same meaning as on the
    review-submission list read) and `lineage_not_backed_by_grant` (new: the
    lineage-previous version is not named by any grant of the chain, so its
    items are not listed; a seal is not refused for this reason). Both flags
    can be present together.
  - Returns carry identifiers only: `returned_by` is the stable
    `user:<uuid>`, never the returner's display name.
  - The request takes no path, body or query parameters — the scope comes
    only from the key's signed grant chain.
  - Refusals reuse existing gate codes: 403 `FORBIDDEN` for a broad key or a
    human session; the gate's 403 `AUTHORING_CAPABILITY_*` codes (missing,
    revoked or exhausted anywhere in the chain, expired, not yet valid,
    integrity); `AUTHORING_CAPABILITY_OUT_OF_SCOPE` when either action is
    missing; `AUTHORING_CAPABILITY_OBJECT_MISMATCH` for a key holding
    `policies:*` beside the carrier scope, or when the capability was carried
    while the read ran.
  - Not in the agent-openapi (ChatGPT Actions) subset.
- **Known limit, unchanged:** no capability read joins the agent licence — it
  is joined only at issuance and at carry — so a revoked licence under
  `enforce` still admits all five capability reads, with one verdict.

## v1.20.0

**Capability-bound draft supersession; the capability carry.** A writer
release: correcting a capability-bound draft now mints a new authoring
capability grant for the correction, and a chain of such grants can be
followed and ended.

- **New: `POST /v1/policies/{id}/versions/{version}/supersede-assigned`.** An
  API key holding only the `authoring:capability` scope, whose capability
  grants `draft.edit` and is bound to exactly this draft, corrects the draft
  by superseding it. In one transaction: the draft is closed `replaced`,
  byte-identical; the corrected rules become a new draft (`codification` is
  required on this route); and a new authoring capability grant is minted for
  the new draft, naming the admitting grant in `succeeds_capability_id`. Every
  other field on the new grant (key, policy, `granted_by`, `grant_authority`,
  actions, source items, window, agent declaration) is copied from the
  admitting grant.
  - Body: `expected_revision`, `rules`, `codification`, `change_reason?`,
    `authoring_capability_id` (must match the admitting capability),
    `additionalProperties: false`.
  - Response `200 { replaced, draft, authoring_capability }`, where
    `authoring_capability` is the new grant plus its derived
    `root_capability_id`. Callers should name the new grant in
    `authoring_capability_id` from then on.
  - Refusals: 400 validation; 403 `AUTHORING_CAPABILITY_ID_MISMATCH`; the
    existing `AUTHORING_CAPABILITY_*` gate codes (re-checked under the row
    lock), including `AUTHORING_CAPABILITY_SUBJECT_NOT_LICENSED`,
    `_SUBJECT_REVOKED` and `_SUBJECT_EXPIRED`; 404; 409 `INVALID_TRANSITION`,
    `STALE_DRAFT_REVISION`, `DRAFT_CONFLICT`, and new 409
    `AUTHORING_CAPABILITY_CHAIN_LIMIT` — a capability a human issued may be
    carried at most 20 times; 422; 500. Nothing is written on any refusal.
  - Not in the agent-openapi (ChatGPT Actions) subset.
- **New: `GET /v1/authoring-capabilities/current`.** Carrier scope only,
  action `policy.read`. Returns the grant that currently governs the calling
  key, without its signature, plus `root_capability_id` — so a caller whose
  supersession response was lost can learn which grant to name next.
- **Revoke: new 409 `AUTHORING_CAPABILITY_CHAIN_ENDED`.** Revoking any grant
  in a chain ends that grant and every grant carried from it, so a grant that
  was itself carried on may still be revoked. A grant whose own ending
  already exists still gets `AUTHORING_CAPABILITY_ALREADY_REVOKED`; a grant
  with no ending of its own but an ended ancestor now gets `CHAIN_ENDED`,
  with `details.ending_record_id`, `ending_record_type` and
  `ended_grant_id`.
- **PATCH and the withdrawal request re-check the capability under locks.** A
  capability-admitted `PATCH /v1/policies/{id}/versions/{version}` and
  `POST /v1/review-submissions/{submissionId}/withdrawal-requests` now lock
  the policy row, then the version row, and re-resolve the admitting
  capability in their own transaction. If it was revoked or exhausted
  anywhere in its chain (including a revocation still in flight when the
  request arrived), expired, or no longer governs because a supersession
  carried it, the write is refused with the same gate 403 code and nothing is
  written. Before this release, a write admitted a moment before a
  revocation could still land after it. Human and broad-key PATCHes are
  unchanged.
- **Seals take the policy row lock before the version row lock.** A seal
  racing a supersession of the same draft no longer risks a 500 from a

## v1.16.0

**The codification lint's findings, on the wire**
- Policy version responses carry an optional `codification_record.lint`. Present only on a version whose write ran the codification lint (an internal, model-assisted check comparing a declared clause's text against the codifier's stored rule); **absent** — not null — on every other version, including one written before the lint existed and one written with the lint disabled.
- Each linted clause carries its `findings` (a code, a message, and diagnostic evidence) and a `needs_context` flag. `status: "ran"` with an empty `findings` array for a clause is a real statement — the lint ran and found nothing — distinct from an absent `lint`, which means the lint never ran at all.
- This is a **projection**, not a mirror, of what is stored internally: it does not include the model's raw per-question answers (only the derived findings), and it does not include token-usage accounting. A finding's `evidence` is likewise limited to the one diagnostic value a reader needs, not the full internal diagnostic bag.

**What it is not**
- It is **advisory**, produced by an automated, model-assisted check. It is **unsigned and unhashed** — not covered by `policy_rules_hash` or `policy_snapshot_digest`, and it enters no receipt, digest, snapshot, export or evidence manifest.
- It is **not part of review or ratification**. A finding is a prompt to whoever is codifying or ratifying the version, never a disposition — it does not change `codification_record.ledger` or `codification_record.counts`.

## v1.14.0

**The codification record: what a version's clauses were accounted for**
- Policy version responses carry an optional `codification_record`. It is present only on versions written through the codification path introduced in 1.13.0, and **absent** — not null — on every other version.
- It records one disposition per **declared** clause, the clause text a reviewer needs in order to judge it, the counts, and any proposal the rule grammar refused.
- The declines are the point. Before this, a clause the codifier read and chose not to express as a rule left no trace once the write completed, so a reviewer could see the rules that were produced but not the judgements behind the ones that were not.
- `ledger`, `counts` and `refusals` are the write boundary's own output, not values the caller supplies. A `codification_record` sent in a request body is ignored.

**What it is not**
- It is **unsigned and unhashed**. It is not covered by `policy_rules_hash` or `policy_snapshot_digest`, and it enters no receipt, snapshot, export or evidence manifest.
- It is **not a sealed review package**. A review package proves byte equality under `meshqu-review-package/v1` and binds source custody; this proves neither. Where a version has both, the review package is the stronger artefact.
- As in 1.13.0, it does **not** establish that the declared clauses are the whole document. Nothing server-side reads the document.

## v1.13.0

**Codification: rule citations are derived, not asserted**
- `POST /v1/policies` and `POST /v1/policies/{id}/versions` accept an optional `codification` block: the clauses the caller read, a map from rule code to clause, and a disposition (`ambiguous`, `unsupported`, `non_normative`) with a reason for every clause that produced no rule.
- When it is supplied, each stored rule's `source_ref` is **derived from the clause it is mapped to**, and any `source_ref` sent in the request is ignored. A rule that names no clause cannot be stored through this path.
- Refusals return `422 CODIFICATION_REFUSED` with the specific reason in `details.code` — a clause with no outcome, a disposition with no reason, or a rule whose condition the evaluator cannot execute.
- **Omitting the block leaves behaviour exactly as before.** Existing callers are unaffected.

**What this establishes, precisely**
- That every clause the caller *declared* has exactly one accounted-for outcome, and that every stored rule is executable and attributed to a declared clause with a citation the API derived rather than accepted.
- It does **not** establish that the declared clauses are the whole source document. Nothing server-side reads the document, so a caller that under-reports both its clauses and their outcomes cannot be distinguished from one that does not. That remains a question for human review before ratification.

## v1.12.0

**Evaluation results say where a rule came from**
- `POST /v1/decisions/evaluate` and `POST /v1/decisions/record` may now return `rule_sources`: a map from rule code to the source reference its author recorded (`document`, `section`, `url`). Present only when at least one rule in the governing snapshot carries one.
- It sits **beside** `result`, not inside it. `result` is the signed object and its `integrity_hash` covers the violations exactly as the evaluator produced them, so a caller joins `rule_sources` to `violations[].rule_code` or `na_rules[].rule_code` itself. Existing clients that ignore the field see unchanged bodies.
- What it is evidence of, stated precisely: `source_ref` is author-supplied and is **excluded** from `policy_rules_hash`, so ratification does not attest to it. It **is** covered by `policy_snapshot_digest`, which hashes the snapshot rules verbatim — so a v2 receipt binds that this snapshot carried this reference. That is a narrower claim than "the rule faithfully encodes that clause", which no digest can make.

**Corrections to the published contract**
- `components.schemas` now defines `def-0`, the recursive `when` gate union. The spec had referenced it 32 times without defining it, affecting nine operations including `POST /v1/policies` and `POST /v1/policies/validate`. Anything that resolves references — an OpenAPI validator, a client generator, an agent importing the schema — previously had nothing to resolve it to. The generator now hoists recursive definitions and refuses to emit a document containing an unresolvable reference.

## v1.11.0

**Ungoverned evaluations are distinguishable from a governed pass**
- `POST /v1/decisions/evaluate` and `POST /v1/decisions/record` may now return an optional `governance_coverage` object when no applicable rule was evaluated. It carries `permission_established: false`, saying explicitly that an `ALLOW` over zero evaluated rules records the absence of an applicable ratified rule rather than a determination that the action is permitted.
- The object is **unsigned and is not a receipt field**. No hash payload, signing envelope, canonical profile or `receipt_schema_version` changed, and stripping the object does not affect the signed payload. Existing receipts verify exactly as before.
- It is **absent** on a governed pass, so a client that ignores it sees byte-identical response bodies to v1.10.0. Treating its absence as permission is a client error.
- `coverage` distinguishes `NO_ACTIVE_RULES` from `NO_APPLICABLE_RULES`. `cryptographically_established` is `true` only for `NO_ACTIVE_RULES`, and only when `evaluated_rules_hash` equals the empty-active-set hash *and* the result is signed — it means the claim is bound into a signed payload, not that the signature has been verified.
- Note `POST /v1/decisions/evaluate` continues to answer `404 NO_ACTIVE_RULES` when a decision type resolves to no active rules at all; it refuses the evaluation rather than returning an advisory. The advisory's reachable case is active rules that are all excluded by their `when` gates.

**Malformed rule conditions are refused rather than silently passing**
- A rule whose condition the evaluator cannot execute — an unrecognised operator key, no subject field, or no executable constraint — is now rejected at the write boundary with `VALIDATION_ERROR` on draft update and on ratify, and produces `UNKNOWN_CONDITION_SHAPE` (`400`) at evaluation time.
- Previously such a condition was skipped and counted as a rule that had passed. A threshold rule written `{ field, operator: "gt", value: 150 }` — not the canonical `{ field, min | max | greater_than | less_than }` — permitted any amount while reporting `rules_evaluated: 1, violations: 0, decision: "ALLOW"`.
- A boolean temporal operator set to `false` (`not_expired`, `not_future`, `must_be_before`, `must_be_after`) and `min_length: 0` are likewise refused: the evaluator reads none of them, so they asked nothing. Numeric bounds of `0` are unaffected and remain executable — `{ field, max: 0 }` still refuses any positive value.
- Rules already stored are unaffected until they are next edited or ratified.

**Corrections to the published contract**
- `PATCH /v1/policies/{id}/versions/{version}` now answers `409 NOT_DRAFT` for a submitted or ratified version even when the submitted rules are also malformed. It previously answered `422` in that case, reporting a rule problem where the version was not editable at all.
- The temporal rule condition schema documents `min_days_after`, `must_be_before` and `must_be_after`. All three were already executed by the evaluator and missing from the published schema.
- Policy list endpoints document the `q` search parameter, and policy version responses document `draft_revision`. Both shipped earlier and had not been regenerated into the spec.

## v1.10.0

**Case-insensitive policy `when` gates**
- `when` gates with `equals` or `in` accept an opt-in `case_sensitive: false`, which folds string-vs-string comparisons only. Booleans and numbers always compare strictly, and gates never coerce types — a boolean `true` is never matched by the string `"true"`.
- An absent key means strict comparison, exactly as before: every previously authored rule and every ratified policy version evaluates byte-identically. There is no schema default — absence is the canonical strict spelling.
- Note the default is deliberately the opposite of the list-*condition* `case_sensitive` (which defaults to `false`): gates match ratified domains, list conditions match free text.

**OpenAPI spec refresh**
- The published spec now also reflects earlier shipped work it had lagged behind: the signed `/v1/.well-known/trust-registry` endpoint and the matching `signing-keys` deprecation notice, boolean members in `when.in` lists, and admin member invitations by email with `actor_email` in audit views.
