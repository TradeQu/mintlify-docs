<Info>
MeshQu is currently available for research, evaluation and design-partner deployments. Production availability and support commitments are agreed per engagement. This changelog documents API and SDK functionality shipped into those deployments. Console UI changes are not tracked here.
</Info>

MeshQu follows [Semantic Versioning](https://semver.org/). The **API contract version is `v1`** — the `/v1` URL prefix, which is stable and only changes on a major release. The current **release** (this changelog's latest entry, the OpenAPI spec `info.version`, and the API package version) is **1.12.0**.

## Versioning policy

- **Major** (`v2.x`): Breaking changes to request/response contracts or authentication. Announced with a migration guide and deprecation period.
- **Minor** (`v1.2`): New endpoints, fields, or features. Backwards-compatible.
- **Patch** (`v1.1.1`): Bug fixes and performance improvements. No contract changes.

## Stability guarantees

- Existing response fields are never removed or renamed within a major version.
- New optional fields may be added to responses at any time — clients should ignore unknown fields.
- Webhook payload schemas follow the same policy.

## API version header

All endpoints are prefixed with `/v1`. When a new major version is released, the previous version will remain available for a documented deprecation period.

## v1.12.0

**Evaluation results say where a rule came from**
- `POST /v1/decisions/evaluate` and `POST /v1/decisions/record` may now return `rule_sources`: a map from rule code to the source reference its author recorded (`document`, `section`, `url`). Present only when at least one rule in the governing snapshot carries one.
- It sits **beside** `result`, not inside it. `result` is the signed object and its `integrity_hash` covers the violations exactly as the evaluator produced them, so a caller joins `rule_sources` to `violations[].rule_code` or `na_rules[].rule_code` itself. Existing clients that ignore the field see unchanged bodies.
- What it is evidence of, stated precisely: `source_ref` is author-supplied and is **excluded** from `policy_rules_hash`, so ratification does not attest to it. It **is** covered by `policy_snapshot_digest`, which hashes the snapshot rules verbatim — so a v2 receipt binds that this snapshot carried this reference. That is a narrower claim than "the rule faithfully encodes that clause", which no digest can make.

**Corrections to the published contract**
- `components.schemas` now defines `def-0`, the recursive `when` gate union. The spec had referenced it 32 times without defining it, affecting nine operations including `POST /v1/policies` and `POST /v1/policies/validate`. Anything that resolves references — an OpenAPI validator, a client generator, an agent importing the schema — previously had nothing to resolve it to. The generator now hoists recursive definitions and refuses to emit a document containing an unresolvable reference.

## v1.11.0

**Ungoverned evaluations are distinguishable from a governed pass**
- `POST /v1/decisions/evaluate` and `POST /v1/decisions/record` may now return an optional `governance_coverage` object when no applicable rule was evaluated. It carries `permission_established: false`, saying explicitly that an `ALLOW` over zero evaluated rules records the absence of an applicable ratified rule rather than a determination that the action is permitted.
- The object is **unsigned and is not a receipt field**. No hash payload, signing envelope, canonical profile or `receipt_schema_version` changed, and stripping the object does not affect the signed payload. Existing receipts verify exactly as before.
- It is **absent** on a governed pass, so a client that ignores it sees byte-identical response bodies to v1.10.0. Treating its absence as permission is a client error.
- `coverage` distinguishes `NO_ACTIVE_RULES` from `NO_APPLICABLE_RULES`. `cryptographically_established` is `true` only for `NO_ACTIVE_RULES`, and only when `evaluated_rules_hash` equals the empty-active-set hash *and* the result is signed — it means the claim is bound into a signed payload, not that the signature has been verified.
- Note `POST /v1/decisions/evaluate` continues to answer `404 NO_ACTIVE_RULES` when a decision type resolves to no active rules at all; it refuses the evaluation rather than returning an advisory. The advisory's reachable case is active rules that are all excluded by their `when` gates.

**Malformed rule conditions are refused rather than silently passing**
- A rule whose condition the evaluator cannot execute — an unrecognised operator key, no subject field, or no executable constraint — is now rejected at the write boundary with `VALIDATION_ERROR` on draft update and on ratify, and produces `UNKNOWN_CONDITION_SHAPE` (`400`) at evaluation time.
- Previously such a condition was skipped and counted as a rule that had passed. A threshold rule written `{ field, operator: "gt", value: 150 }` — not the canonical `{ field, min | max | greater_than | less_than }` — permitted any amount while reporting `rules_evaluated: 1, violations: 0, decision: "ALLOW"`.
- A boolean temporal operator set to `false` (`not_expired`, `not_future`, `must_be_before`, `must_be_after`) and `min_length: 0` are likewise refused: the evaluator reads none of them, so they asked nothing. Numeric bounds of `0` are unaffected and remain executable — `{ field, max: 0 }` still refuses any positive value.
- Rules already stored are unaffected until they are next edited or ratified.

**Corrections to the published contract**
- `PATCH /v1/policies/{id}/versions/{version}` now answers `409 NOT_DRAFT` for a submitted or ratified version even when the submitted rules are also malformed. It previously answered `422` in that case, reporting a rule problem where the version was not editable at all.
- The temporal rule condition schema documents `min_days_after`, `must_be_before` and `must_be_after`. All three were already executed by the evaluator and missing from the published schema.
- Policy list endpoints document the `q` search parameter, and policy version responses document `draft_revision`. Both shipped earlier and had not been regenerated into the spec.

## v1.10.0

**Case-insensitive policy `when` gates**
- `when` gates with `equals` or `in` accept an opt-in `case_sensitive: false`, which folds string-vs-string comparisons only. Booleans and numbers always compare strictly, and gates never coerce types — a boolean `true` is never matched by the string `"true"`.
- An absent key means strict comparison, exactly as before: every previously authored rule and every ratified policy version evaluates byte-identically. There is no schema default — absence is the canonical strict spelling.
- Note the default is deliberately the opposite of the list-*condition* `case_sensitive` (which defaults to `false`): gates match ratified domains, list conditions match free text.

**OpenAPI spec refresh**
- The published spec now also reflects earlier shipped work it had lagged behind: the signed `/v1/.well-known/trust-registry` endpoint and the matching `signing-keys` deprecation notice, boolean members in `when.in` lists, and admin member invitations by email with `actor_email` in audit views.

## v1.8.0

**Human Decision Capture (Forms)**
- New Forms surface for capturing structured human decisions that produce receipts identical in shape to programmatic decisions.
- Endpoints: `POST /v1/forms`, `GET /v1/forms`, `GET /v1/forms/:formId`, `PATCH /v1/forms/:formId`, `DELETE /v1/forms/:formId`.
- Form schemas and API contracts are introspectable: `GET /v1/forms/:formId/schema`, `GET /v1/forms/:formId/api-contract`.
- Submissions: `POST /v1/forms/:formId/submit` returns a decision receipt; retrieve later via `GET /v1/forms/:formId/receipts/:decisionId`.

## v1.7.0

**Policy v2 Lifecycle (Submit / Reject / Recall)**
- Draft policy versions now move through an explicit lifecycle:
  - `POST /v1/policies/:id/versions/:version/submit` — submit a draft for ratification.
  - `POST /v1/policies/:id/versions/:version/reject` — reject a submitted draft.
  - `POST /v1/policies/:id/versions/:version/recall` — recall a submitted draft back to draft state.
- Additional draft-version endpoints: `GET /v1/policies/:id/versions/:version`, `PATCH /v1/policies/:id/versions/:version`, `DELETE /v1/policies/:id/versions/:version`.
- New `GET /v1/policies/:id/decisions` — list all decisions evaluated against a given policy.

## v1.6.0

**Receipt Schema v2 + Approval Lineage**
- New top-level fields on decision receipts:
  - `receipt_schema_version` — explicit schema version marker.
  - `policy_snapshot_digest` — canonical SHA-256 of the bound policy snapshot.
  - `evidence_manifest_digest` — canonical SHA-256 of the evidence manifest, when present.
- **Policy Approval Receipts** — cryptographic ratifier signatures on the policy version that governed a decision. The offline verifier now accepts ratifier and custodian public-key sets as additional trust roots.
- Two new bundle verifier sub-claims — `evidence` (bundled evidence manifest matches `evidence_manifest_digest`) and `approval_lineage` (per-version approval-receipt digest, ratifier signature and `policy_rules_hash`) — taking the sub-claim set from eight to **ten**.
- All v1 receipts remain verifiable indefinitely — schema v2 fields are additive.

## v1.5.0

**Public Verification Surface**
- New JWKS endpoint: `GET /v1/.well-known/signing-keys` — versioned public signing keys for offline receipt verification.
- New public, unauthenticated endpoints (callers do not need an API key):
  - `GET /v1/receipts/:decisionId` — fetch a signed decision receipt.
  - `GET /v1/receipts/:decisionId/bundle` — download the full Verification Bundle.
  - `GET /v1/chains/:chainId/verify` — verify a chain proof.
  - `GET /v1/chains/:chainId/seal` — read a chain seal.
  - `GET /v1/chains/:chainId/bundle` — download a chain Verification Bundle.
- **Verification Bundles** — self-contained, offline-verifiable archives under a digest-of-digests manifest, with a sub-claim reported per artefact (receipt, policy snapshot, chain proofs, transparency proof, trust roots, canonicalisation). Two further sub-claims (`evidence`, `approval_lineage`) arrived in v1.6.0, bringing the set to **ten**.

## v1.4.0

**Actor Attribution**
- `POST /v1/decisions/record` now accepts an optional top-level `actor` object: `id`, `type`, `role`, `authority`, `display_name`.
- `actor.id` is included in the integrity hash and cryptographically bound to every receipt.
- Other actor fields are stored for audit display.
- Backward compatible: `actor` is optional. If omitted and `context.metadata.actor_id` is present, the API falls back to that value. When `actor.id` is supplied, it takes precedence.
- New `actor` optional parameter on `client.record()` in the TypeScript SDK.
- Decision chain steps can now carry per-step actor attribution, enabling multi-actor chain audit trails.

## v1.3.0

**Structured Violation Reason Codes**
- Every violation now includes a `reason_code` field — a structured code for programmatic aggregation without text parsing.
- 17 reason codes across all rule types: presence (`FIELD_MISSING`, `FIELD_FORBIDDEN`, `FIELD_TOO_SHORT`), temporal (`DATE_EXPIRED`, `DATE_INVALID`, etc.), threshold (`VALUE_ABOVE_MAX`, `VALUE_BELOW_MIN`, etc.), and list (`VALUE_NOT_ALLOWED`, `VALUE_FORBIDDEN`).
- New `ReasonCode` type exported from `@meshqu/types` and re-exported from `@meshqu/client`.
- Backwards compatible: `reason_code` is a new required field on violations. Existing `reason` strings are unchanged.
- **Replay note:** New receipts have different integrity hashes than pre-`reason_code` receipts due to the additional field. Pre-migration receipts remain verifiable against their stored hash.

**Decision Outcomes**
- New `POST /v1/decisions/:id/outcome` endpoint to capture what happened after a verdict.
- Five outcome statuses: `accepted`, `overridden`, `escalated`, `expired`, `abandoned`.
- One outcome per decision (409 on duplicate). Immutable after insert.
- Outcomes included on `GET /v1/decisions/:id` response.
- New `recordOutcome()` method in the TypeScript SDK.

**Violation Analytics & Identifier Stability**
- Violations denormalized into queryable table at write time (analytics projection, not source of truth).
- `GET /v1/decisions` now accepts `correlation_id` query parameter.
- Policy rules accept optional `replaces_rule_code` for advisory lineage tracking.

## v1.2.0

**Conditional Rule Applicability (When Gating)**
- Added optional `when` clause on policy rules — rules are only evaluated when the clause matches the decision context.
- Non-matching rules return NA (not applicable) with a human-readable reason on the decision receipt.
- New optional fields on `EvaluationResult`: `rules_na` (count) and `na_rules` (details).
- Supported `when` operators: `equals`, `in`, `exists`, with `all`/`any` combinators for nested logic.
- Snapshot hash includes `when` clauses (backward compatible — existing hashes unchanged).

**Receipt Signing**
- Decision receipts are now signed with Ed25519 when a signing key is configured.
- Receipts include `signature`, `signature_kid`, and `signature_algorithm` fields.
- Auditors can verify receipts using the public key alone — no shared secret needed.

**Security & Infrastructure**
- Encryption key versioning with rotation support and legacy fallback.
- Rate limiting upgraded to shared state across API replicas.

- Production authentication hardening improvements.
